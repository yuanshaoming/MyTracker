# 行人跟踪模块开发实施计划

## 1. 项目目标

在现有行人检测模块已经能够稳定输出行人边界框的基础上，新增轻量级多目标行人跟踪模块，实现连续图片流中的行人身份保持。

当前运行条件：

- 输入图片流约 8 fps；
- 现有模块已经输出可靠的行人检测框；
- 正式运行平台包括 Windows 11 PC 和 NVIDIA Jetson Xavier NX；
- 开发调试阶段还需要支持 macOS 笔记本；
- 正式软件基于 Qt 5.12；
- 第一阶段不引入 ReID；
- 优先降低 CPU、GPU 和内存占用；
- 跟踪模块不得依赖检测模型类型。

第一阶段采用：

**OC-SORT + Kalman Filter + IoU/运动方向关联 + Hungarian Assignment**

跟踪模块全部运行于 CPU，不占用检测算法使用的 GPU。

---

# 2. 总体开发原则

系统采用“检测与跟踪解耦”的结构：

```text
Existing Detector
       │
       │ Detection[]
       ▼
Tracker Adapter
       │
       ▼
tracker_core
       │
       ├─ Kalman Filter
       ├─ OC-SORT Association
       ├─ Hungarian Assignment
       ├─ Track State Management
       └─ Track History
       │
       ▼
TrackResult[]
       │
       ├─ Qt UI
       └─ Business Logic
```

其中最重要的原则是：

**tracker_core 不直接依赖 Qt。**

也就是说核心代码中不使用：

```text
QRect
QPoint
QString
QObject
QThread
```

而使用标准 C++ 数据结构。

Qt 工程只负责：

```text
现有Detection
      ↓
转换
      ↓
tracking::Detection
      ↓
tracker.update()
      ↓
tracking::TrackResult
      ↓
Qt显示 / 业务处理
```

这样同一套跟踪算法可以直接运行在：

```text
macOS
Windows 11
Jetson Xavier NX
```

Mac 开发阶段甚至可以完全不安装 Qt，只运行算法测试程序。

# 5. 核心接口设计

## Detection

```cpp
struct BBox
{
    float x1;
    float y1;
    float x2;
    float y2;
};

struct Detection
{
    BBox bbox;
    float confidence = 1.0f;
    int classId = 0;
};
```

这里不要直接使用 `cv::Rect` 或 `QRectF`。

这样算法层完全独立。

## TrackResult

```cpp
enum class TrackState
{
    Tentative,
    Confirmed,
    Lost
};

struct TrackResult
{
    int trackId = -1;

    BBox bbox;

    float confidence = 0.0f;

    TrackState state;

    float velocityX = 0.0f;
    float velocityY = 0.0f;

    int age = 0;
    int lostFrames = 0;
};
```

## Tracker接口

```cpp
class ITracker
{
public:
    virtual ~ITracker() = default;

    virtual std::vector<TrackResult> update(
        const std::vector<Detection>& detections,
        int64_t timestampMs) = 0;

    virtual void reset() = 0;
};
```

以后即使更换：

```text
OC-SORT
ByteTrack
SORT
```

业务层也无需修改。

# 6. 首先建立 Detection Replay 机制

这是本项目非常重要的一步，应当在开发 OC-SORT 之前完成。

现有设备检测模块增加一个调试输出功能，把每帧检测结果保存为：

```text
frame_id
timestamp
x1
y1
x2
y2
confidence
```

例如：

```text
1,0,75,40,143,420,0.96
2,125,73,42,141,421,0.95
3,250,70,44,139,423,0.97
```

建议采用 CSV。

同时保存对应图片序列：

```text
000001.jpg
000002.jpg
000003.jpg
...
detections.csv
```

这样 Mac 上就不需要运行设备检测算法。

可以直接：

```text
detections.csv
        ↓
tracker_replay
        ↓
OC-SORT
        ↓
Track ID
```

以后任何算法参数调整，都可以对完全相同的数据重复测试。

这一机制对于后续 Codex 开发、Bug 复现和算法回归测试非常重要。

# 10. 第四阶段：升级为 OC-SORT

增加 OC-SORT 的三项关键机制：

```text
Observation-Centric Momentum
Observation-Centric Recovery
Observation-Centric Re-Update
```

重点实现：

### 历史 Observation

保存一定数量真实 Detection：

```text
Track:

Observation(t)
Observation(t-1)
Observation(t-2)
Observation(t-3)
```

不要只依赖 Kalman Prediction。

---

### 运动方向

利用历史真实 Detection：

```text
previous observation
        ↓
current observation
        ↓
direction vector
```

参与数据关联。

OC-SORT官方实现默认：

```text
delta_t = 3
inertia = 0.2
IoU threshold = 0.3
```

这些值可作为最初的参考值，而不是直接作为最终设备参数。citeturn363955view2turn363955view3

---

### 二次关联

第一次：

```text
Detection
    ↕
Kalman Prediction
```

未匹配目标再次利用：

```text
Last Observation
        ↕
Unmatched Detection
```

进行恢复。

这部分对人员短时遮挡尤其重要。

# 11. 第五阶段：针对8 fps进行优化

完成标准 OC-SORT 后，再针对设备场景修改。

不要一开始就修改原算法，否则出现问题时难以区分：

```text
算法实现错误
还是
低帧率优化导致的问题
```

首先建立：

```text
OCSORT_STANDARD
```

然后增加：

```text
OCSORT_8FPS
```

配置开关。

重点测试以下优化。

### Track生命周期时间化

不要简单沿用：

```text
max_age = 30
```

因为8 fps时：

```text
30帧 = 3.75秒
```

建议第一版：

```text
minHits = 2

lostTimeout ≈ 1000 ms
removeTimeout ≈ 1500 ms
```

内部根据实际帧率换算。

---

### Timestamp支持

每次：

```cpp
tracker.update(detections, timestampMs);
```

计算：

```text
Δt
```

正常：

```text
≈125ms
```

遇到掉帧：

```text
250ms
375ms
```

仍能识别真实时间跨度。

动态时间 Kalman 可以作为第二阶段优化，通过配置启用，并与标准 OC-SORT 做 A/B 对比。

# 12. Track状态管理

业务层建议采用：

```text
Tentative
     │
     │ 连续2次检测
     ▼
Confirmed
     │
     │ 暂时没有Detection
     ▼
Lost
     │
     ├──重新匹配──→ Confirmed
     │
     │ Timeout
     ▼
Removed
```

注意：

`Removed` 不需要向业务层持续输出。

例如：

```text
Frame 100
Person → ID 12

Frame 101
ID 12

Frame 102
遮挡

Frame 103
遮挡

Frame 104
重新检测
```

预期：

```text
Frame 104仍然是 ID 12
```

而不是创建新的 ID。

# 22. 线程安全要求

第一阶段明确规定：

**一个 Tracker 实例只服务一个图片流。**

不要：

```text
多个线程
同时调用
同一个tracker.update()
```

正确方式：

```text
Camera1
→ Tracker1

Camera2
→ Tracker2
```

这样算法内部无需大量锁。

如果以后支持多路视频：

```text
N路摄像头
=
N个Tracker实例
```

可以由线程池调度。
